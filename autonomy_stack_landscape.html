01
Math foundations
Enabler — not a domain you build systems in, but the language everything is written in
Partial
▼
Gap from ML math to estimation math
Your ML background gives you linear algebra and probability at the right level for backprop and loss surfaces. Estimation needs three extra things: Gaussian conditioning (the math behind the Kalman update), Jacobians (how you linearize a nonlinear function — the EKF's core operation), and state-space notation (how physical systems are written as x(k+1) = Ax(k) + Bu(k) + w(k)).
Specific things to learn
  • Conditional Gaussian distributions: given joint Gaussian p(x,y), what is p(x|y)? This derivation IS the Kalman update step.
  • Jacobian matrices: how to linearize f(x) around an operating point x₀. If you can compute ∂f/∂x, you can implement any EKF.
  • State-space representation: x = Ax + Bu + w, y = Cx + v. Learn to read this fluently.
  • ODE integration: Euler and RK4. Needed to simulate physical systems for testing your estimators and controllers.
    • Do this first
    Derive the Kalman filter from scratch Pen and paper. Start from Bayesian conditioning of two Gaussians, derive the predict and update equations. One afternoon. Makes everything else obvious. Use Labbe's "Kalman Filters in Python" Ch.1 as the guide.
    Resources
    Labbe's "Kalman and Bayesian Filters in Python" (free, filterpyrepository) · Barfoot "State Estimation for Robotics" Appendix A (free PDF) · 3Blue1Brown eigenvectors video if you're rusty
    02
    Probabilistic estimation
    The mathematical heart of the stack — every autonomous system is an estimation problem
    Priority next
    ▼
    What it is
    Tracking the state of a system over time given noisy, incomplete observations. The hidden state could be a drone's position, a submarine's heading, an aircraft's trajectory, or a battery's internal resistance. The math is the same. This is the one domain where getting deeply good has compounding returns across every other domain in the stack.
    Your bridge
    Your LSTM-Transformer RUL model IS an estimation system — you're estimating a hidden degradation state from noisy cycle observations. You did it with a learned model. The Kalman filter family does it with an analytical model. Understanding both gives you something most ML engineers and most control engineers don't have: the ability to choose the right tool. When data is abundant and dynamics are complex → learned estimation. When data is sparse and physics is known → analytical estimation. Often you combine them (deep Kalman filter, learned process model inside an EKF framework).
    The progression
  • Kalman Filter (KF) — linear systems, Gaussian noise. Simplest case. Radar tracking, GPS smoothing. Start here.
  • Extended Kalman Filter (EKF) — nonlinear systems, linearized via Jacobians. UAV position estimation, robot odometry. The industry workhorse.
  • Unscented Kalman Filter (UKF) — nonlinear, sigma-point approximation. More accurate than EKF for highly nonlinear systems, no Jacobians required.
  • Particle Filter — non-Gaussian, non-linear, general. Used when dynamics are highly nonlinear or multi-modal (e.g., tracking a target that could be at one of several locations).
  • Factor Graphs — modern formulation, used in SLAM and multi-sensor fusion. GTSAM/g2o. Worth understanding conceptually even if not implementing immediately.
    • Build — in this order
    Rust 1D Kalman filter Estimate position from noisy GPS measurements. No matrices, just scalars. Focus on the predict/update loop and watching the uncertainty collapse as observations arrive. 1–2 days.
    Rust EKF for 2D vehicle tracking State vector [x, y, heading, speed]. Nonlinear motion model (constant velocity, turning). Noisy [x,y] observations. Implement the Jacobian manually. This is the canonical EKF example — exists in every robotics course. 1 week.
    Bridge Battery SOH with EKF Replace your LSTM with an analytical degradation model inside an EKF. State = [capacity_fade_rate, internal_resistance]. Observation = voltage/capacity measurements. This is the key bridge project: same domain you know deeply, different estimation framework. You'll viscerally understand what KF can't do (it assumes linear-ish dynamics) and what your LSTM does better (captures complex nonlinear path-dependence). A proper comparison of both approaches on your data is a paper-worthy result.
    Rust IMU + GPS fusion with EKF The canonical aerospace example. Fuse accelerometer/gyroscope (high frequency, drifting) with GPS (low frequency, accurate). This exact code runs in every UAV, every autonomous vehicle, every spacecraft. 1–2 weeks.
    Resources
    Thrun, Burgard, Fox — "Probabilistic Robotics" Ch.3–4 (THE reference) · Labbe's free Jupyter book (interactive, excellent) · Barfoot "State Estimation for Robotics" (rigorous, Lie groups, the advanced path)

    04
    Real-time systems
    Cross-cutting substrate — everything in the stack runs on this
    Starting
    ▼
    What real-time means
    Deterministic, not fast. Your code must complete in a guaranteed time budget — always, not on average. A 50ms jitter spike in a UAV attitude controller during a maneuver is a crash, not a latency metric. This rules out garbage collection, unbounded heap allocation, and mutexes that can block indefinitely. Rust was built for exactly this reason.
    The mental model shift
    In application code, you ask "does this work?" In real-time code, you ask "does this work AND finish in ≤N microseconds on worst-case input?" Every data structure, every allocation, every lock must be analyzed for its worst-case behavior, not average behavior.
    Things to learn
  • Rust no_std: what the standard library actually provides and what you lose without it (heap allocation, threads, file I/O). Writing no_std Rust is writing for embedded/RTOS targets.
  • Allocation discipline: why Vec::push on a hot path is dangerous (hidden realloc). Stack allocation, fixed-size arrays, pre-allocated buffers. The heapless crate.
  • Lock-free data structures: atomic operations, memory ordering (Acquire/Release/SeqCst), MPSC queues without mutexes. Needed for sensor data flowing between threads.
  • RTOS concepts: task scheduling (rate monotonic scheduling), priority inversion, deadline guarantees. Even if you never write RTOS code directly, understanding this lets you reason about why embedded firmware is structured the way it is.
  • DDS (Data Distribution Service): the publish-subscribe standard that Anduril's Lattice, ROS2, and the F-35 all use. Topics, QoS policies (reliability, deadline, lifespan). Look at Zenoh — a Rust-native DDS-style system.
    • Build
    Rust Lock-free ring buffer for sensor data Implement a fixed-capacity ring buffer using atomics and no mutexes. Producer thread writes sensor readings, consumer thread reads them. Benchmark it against Mutex<VecDeque>. Already in your roadmap — this is the right project.
    Rust Minimal pub/sub message bus Topics as typed channels, subscribers register interest, publisher sends to all subscribers. No heap allocation on the message path. This is DDS in miniature — you'll understand why Anduril uses it to connect their sensor nodes to their mission system. Eventually look at Zenoh for the real thing.
    Resources
    Rust embedded book (docs.rust-embedded.org) · "Real-Time Systems" by Liu Ch.1–3 · Zenoh documentation (zenoh.io) · heapless crate documentation
    05
    Control theory
    Given state estimate, compute inputs to achieve desired behavior
    Not started
    ▼
    What it is
    Estimation answers "where am I?" Planning answers "where should I go?" Control answers "what do I do with my actuators right now to get there?" These are distinct problems. PID is the simplest controller. LQR is optimal for linear systems. MPC runs an optimization loop in real time and handles constraints (don't exceed max thrust, stay within geofence).
    Your bridge
    You understand optimization from ML training. LQR is literally solving a minimization problem: find control inputs u that minimize a cost function J = Σ(xᵀQx + uᵀRu). MPC is running gradient descent on a prediction horizon in real time. The intuition transfers — the math notation is different but the concept is the same.
    The progression
  • PID controller: proportional + integral + derivative. The building block. Found in every motor driver, every temperature regulator, every quad rotor inner loop. Learn Ziegler-Nichols tuning. Implement one in Rust.
  • Stability analysis: eigenvalues of the closed-loop system matrix. A controller is stable if all eigenvalues have negative real parts. This lets you reason about whether your controller will converge or oscillate.
  • Linear Quadratic Regulator (LQR): optimal control for linear systems. Solve the algebraic Riccati equation, get the optimal feedback gain matrix K. Used in UAV attitude control, spacecraft pointing, robotic arm joints.
  • Model Predictive Control (MPC): simulate N steps into the future, find the input sequence that minimizes cost over that horizon, apply first input, repeat. Handles constraints. Used in autonomous vehicles and advanced UAV trajectory following.
    • Build
    Rust PID for a simulated 1D system Mass-spring-damper or simple DC motor. Tune it. Watch it overshoot, undershoot, oscillate. Tune the gains manually and then with Ziegler-Nichols. Building this in Rust with a timestep loop is also an exercise in deterministic simulation — important for testing real-time systems.
    Rust LQR for an inverted pendulum The canonical control theory demo. Balance a pole on a cart. State = [cart position, cart velocity, pole angle, pole angular velocity]. Solve the Riccati equation (can compute offline, hardcode gains for the simulation). Gives deep intuition for how LQR trades off state error vs. control effort via the Q and R matrices.
    Resources
    Brian Douglas YouTube channel (best control theory explainers on the internet) · "Control System Design" by Goodwin et al. Chs.1–6 · Steve Brunton's "Data-Driven Control" lectures (connects control to ML, highly relevant for you)
    06
    Planning & decision
    Given state and goal, find a feasible path or action sequence
    Not started
    ▼
    What it is
    Two distinct sub-problems: path planning (find a geometric path from A to B avoiding obstacles) and trajectory optimization (find a dynamically-feasible, minimum-cost trajectory — respecting the system's physics). Behavior trees sit above both: they define the hierarchical logic for when to plan, when to execute, when to abort.
    Your bridge
    Graph search (A*) is just algorithms, which you know. The harder part is trajectory optimization, which is constrained optimization — and you have intuition for that from ML. The new concept is the dynamics constraint: the path has to be followable given your system's physics (max acceleration, turn radius, etc.).
    The progression
  • A* and D* Lite: graph search on discrete/grid worlds. Foundation. D* Lite replans efficiently when the map changes.
  • RRT / RRT*: sampling-based planning for continuous state spaces. Grows a random tree, finds path. RRT* converges to optimal path given enough time. Standard for robotic arm planning and UAV obstacle avoidance.
  • Trajectory optimization: CHOMP (gradient descent on path), iLQR (iterative LQR, produces locally optimal trajectories). This is where planning meets control. Every trajectory-following drone uses something like this.
  • Behavior trees: hierarchical task decomposition. Nodes: Sequence (do A then B), Selector (try A, if fail try B), Condition (is X true?), Action (do Y). The standard architecture for autonomous system behavior in defense and robotics — Anduril, Boston Dynamics, and ROS2 all use them.
    • Build
    Rust RRT for 2D obstacle avoidance Random 2D environment with circular obstacles. Grow a tree from start, find path to goal. Visualize the tree growing. Extend to RRT* and watch paths improve. 3–5 days.
    Rust Behavior tree executor Implement the core node types (Sequence, Selector, Action, Condition, Parallel). Tick-based execution. This is the architecture that coordinates the full autonomy loop — "if obstacle detected: stop → replan → resume, else: track waypoint." Your AI agents background actually maps here — both are hierarchical task orchestration.
    Resources
    LaValle "Planning Algorithms" (free at planning.cs.uiuc.edu, the reference textbook) · "Behavior Trees in Robotics and AI" by Colledanchise & Ögren · BehaviorTree.CPP library (C++ but excellent architecture reference)
    07
    Mission & autonomy
    Coordinating multiple capabilities toward mission objectives — Lattice is this layer
    Adjacent
    ▼
    What it is
    The highest-level layer: multi-agent coordination, fault-tolerant mission execution, human-machine teaming, distributed state sharing across vehicles. Anduril's Lattice platform is an implementation of this layer — it connects drones, ground vehicles, sensors, and human operators into a shared operational picture and coordinates their behavior toward mission goals.
    Your bridge
    Your AI agents work (the Teams bot, the Voltaiq replacement, multi-tool orchestration) maps directly here. Both are hierarchical task orchestration with tool/capability routing. The difference is latency constraints (mission systems run in seconds, not minutes) and the nature of the tools (physical effectors, not API calls). Your battery intelligence platform's architecture — intent classification → tool routing → result synthesis — is conceptually the same as a mission planner routing to sensing, navigation, and communication capabilities.
    Things to understand
  • Multi-agent task allocation: N vehicles, M targets, assign optimally. Hungarian algorithm for simple cases. Auction algorithms for decentralized settings. Coalition formation for complex tasks.
  • Consensus and distributed state: how do 10 drones agree on a shared picture of the world when they're communicating over a lossy radio link? Raft/PBFT concepts. Relevant to Lattice's tactical data link architecture.
  • Human-machine teaming: mixed-initiative systems where human and autonomous agents share control. Supervisory control theory. When does the system ask for human authorization vs. act autonomously? This is Anduril's central design challenge.
  • ROS2: even though defense systems don't use ROS2 directly, it implements the full autonomy stack (DDS, behavior trees, sensor drivers, visualization) and is the best pedagogical environment for understanding how all the layers connect.
    • Build
    Agents Multi-agent task allocator N simulated UAVs, M targets in a 2D map. Implement the Hungarian algorithm for global optimal allocation, then implement an auction protocol for decentralized allocation. Compare. This is the core of any multi-vehicle coordination system.
    Agents Fault-tolerant mission planner A mission that replans when sensors fail or waypoints become unreachable. Uses behavior trees (domain 6) for the execution layer and EKF (domain 2) for localization. Connects the stack.

    ROS2 documentation + Nav2 stack (the full autonomous navigation reference) · "Multiagent Systems" by Shoham & Leyton-Brown · Anduril's public talks on Lattice architecture (YouTube)
